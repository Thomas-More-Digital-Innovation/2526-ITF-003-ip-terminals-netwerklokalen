# 8.3 You automate system administration tasks with Linux service management

## 1. Project Overview
The IP Terminal is a rackmounted network appliance based on a Raspberry Pi 4. It features an integrated SPI display, three physical buttons, and a joystick. The primary goal of this device is to provide a dedicated hardware interface for managing the Pi's networking configuration (IPv4, IPv6, DHCP, and DNS) directly from the rack, without requiring an external keyboard, monitor, or SSH access.

## 2. NixOS on Raspberry Pi
For this project, I chose NixOS as the operating system. NixOS's declarative nature is ideal for building specialized appliances like the IP Terminal. The entire system state, from the Linux kernel and hardware overlays (like SPI for the display) to the Python application and systemd services is defined in a single configuration file (`flake.nix`). This ensures that the terminal's behavior is consistent, reproducible, and easy to redeploy.

### 2.1 Why Nix Flakes?
While traditional NixOS uses "channels" (stateful pointers to package sets), I used Nix Flakes for this project to achieve full reproducibility.

*   **Traditional NixOS**: Relies on `nix-channel`, which can differ between machines. Building the same configuration on two different days might result in different package versions if the channel was updated in between.
*   **Nix Flakes**: Uses a `flake.lock` file that pins every dependency (including `nixpkgs` and hardware overlays) to a specific git commit hash. This ensures that the terminal build is identical every single time, regardless of which machine it is built on or when the build occurs.

To ensure the IP Terminal is always functional and accessible upon booting the Raspberry Pi, I configured a **systemd service** within the NixOS configuration. This service automatically starts the Python-based control application, which manages the terminal's networking settings through the connected LCD and physical controls.

## 3. Defining the systemd Service in NixOS

In NixOS, services are defined declaratively in the configuration. The `systemd.services` option allows for a structured way to define how an application should run, its dependencies, and its lifecycle.

### 3.1 What is `multi-user.target`?
In systemd, **targets** act as synchronization points for the boot process, roughly equivalent to "runlevels" in older Linux systems.

The **`multi-user.target`** is the standard target for a system that is fully booted and ready to support multiple users, either via local login or network services (like SSH). It represents a stable, non-graphical multi-user environment. 

I configured the `ip-terminal` service to be pulled in by this target (via the `wantedBy` option), ensuring it starts automatically during the final phase of the normal boot sequence once core services are active.

### Service Configuration:
```nix
systemd.services.ip-terminal = {
  description = "IP Terminal Main Service";
  after = [ "network-online.target" ];
  wants = [ "network-online.target" ];
  path = with pkgs; [ networkmanager dialog ncurses ];
  serviceConfig = {
    Type = "simple";
    ExecStart = "/opt/venv/bin/python /opt/ip-terminal-code/main.py";
    WorkingDirectory = "/opt/ip-terminal-code";
    Environment = [
      "PYTHONUNBUFFERED=1"
      "FONT_PATH=${pkgs.dejavu_fonts}/share/fonts/truetype/DejaVuSans.ttf"
    ];
    Restart = "always";
    User = "root";
  };
  wantedBy = [ "multi-user.target" ];
};
```

### Key Components of the Service:
*   **`after` & `wants`**: The service waits for `network-online.target`, ensuring the networking stack is ready before the application attempts to read or modify settings via `nmcli`.
*   **`ExecStart`**: Points to the Python interpreter within a custom virtual environment (`/opt/venv/bin/python`) and executes the entry point of the application (`main.py`).
*   **`Restart = "always"`**: If the Python application crashes, systemd will automatically restart it.
*   **`User = "root"`**: This defines that the service will run as the root user, having full administrative privileges over the system. This is necessary because the application must interact with physical GPIO pins and use `nmcli` to modify system-wide network configuration.
*   **`Environment`**: This allows passing environment variables to the service. For the IP Terminal, I configured `PYTHONUNBUFFERED=1` to ensure that Python logs are sent immediately to `journalctl` without buffering, and `FONT_PATH` to tell the application where to find the fonts required for the LCD display.

## 4. The Python Application Logic

The application has multiple modes. When started by the systemd service (without arguments), it defaults to **Hardware Mode**, which utilizes the Waveshare LCD HAT and its joystick for input. However, it can also be run in **TUI Mode**, which uses the terminal for input and output.

### Application Entry Point:
```python
if __name__ == "__main__":
    parser = argparse.ArgumentParser(description="IP Terminal Configurator")
    parser.add_argument(
        "--tui",
        action="store_true",
        help="Run in TUI (dialog) mode instead of hardware mode.",
    )
    args = parser.parse_args()

    if args.tui:
        run_tui()
    else:
        run_hardware()
```

By running this as a systemd service, the terminal becomes a dedicated appliance. Users can configure the IP address, prefix, gateway, and DNS directly from the device's physical interface as soon as it powers on, without needing a keyboard or a network connection first.
